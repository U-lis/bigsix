# 프로그램 세션 엔진 (Program & Session Engine) - Specification

**Target Version**: 0.1.0
**Work Type**: feature
**Base Branch**: `main`
**Working Branch**: `feature/program-session`
**Source Conversation**: prefill

---

## Overview

**Purpose**
`bigsix`는 폴 웨이드 『죄수 운동법』(비타북스, 2017)의 빅6 — 6종목 × 10단계 — 훈련 프로그램을 진행시키는 엔진이다.
앱의 목적은 두 가지다.

1. 선택한 루틴에 따라 **매일 무엇을 얼마나 할지** 알려준다.
2. 기준에 도달하면 **다음 단계로 승급**시킨다.

**Problem**
현재 커밋(`531fb61`) 기준으로 단계별 목표 계산(`planExercise`), 승급 판정(`evaluateSession`),
다지기(`planConsolidation`), 해금 판정(`checkGate`), 요일별 계획(`planDay`)은 이미 동작한다.
그러나 다음이 빠져 있어 "오늘 무엇을 할지"를 실제 달력 위에서 굴릴 수 없다.

- `AppState`에 **현재 수행 중인 프로그램(루틴)** 정보가 없다. `planDay`가 매번 `programId`를 인자로 받는다.
- 실제 `Date`가 아니라 `'월'` 같은 **요일 문자열**을 받는다.
- 프로그램 **전환**(수동/자동 제안)이라는 개념이 없다.
- **좌우 구분 단계**에서 어느 쪽을 입력해야 하는지 사용자에게 알릴 방법이 없다.
- **미수행일**이 남지 않는다. 계획이 있었는데 하지 않은 날이 조회 결과에서 사라진다.

**Solution**
`AppState`에 프로그램 구간(segment) 개념을 도입하고, 날짜 기반 계획·조회 API와
프로그램 전환(수동 + 자동 제안) 로직을 엔진 레이어에 추가한다. **이번 작업은 엔진만 다룬다.**

## Functional Requirements

### Core Features

#### FR-1: 좌우 기록 — 약한 쪽 기준 입력

- [ ] FR-1.1: `perSide: true`인 단계에서는 **양쪽을 모두 수행하되, 적게 한 쪽(약한 쪽)의 수치 하나만** 기록한다.
      `SessionRecord.sets`는 지금과 동일하게 값 하나만 담는다. 좌/우를 분리 저장하지 않는다.
- [ ] FR-1.2: 계획 결과(`PlannedExercise`)에 **사용자 고지용 문자열 필드**를 추가한다.
      값 예시: `"양쪽 팔을 모두 수행하고, 적게 한 쪽의 횟수를 입력한다."`
- [ ] FR-1.3: 고지 문구의 부위 명칭은 종목에 따라 나눈다.
      - `squat` → **다리**
      - `pushup`, `pullup`, `hspu` → **팔**
- [ ] FR-1.4: `perSide`가 아닌 단계에서는 이 필드를 비운다(`undefined`).
- [ ] FR-1.5: 이 고지는 **표시용 사실 문구**이며 계산에 관여하지 않는다.
      기존 `planExercise` / `evaluateSession`의 수치 판정 로직은 바뀌지 않는다.

> **확정 (데이터 확인 완료)**: `data/progressions.json`의 `perSide: true` 단계는 **총 16개**다
> — `pushup` / `squat` / `pullup` / `hspu` 각각 7~10단계 (4종목 × 4단계 = 16).
> `legraise` · `bridge`에 `perSide`가 없는 것은 **데이터 누락이 아니라 정확한 값**이며,
> 데이터 수정은 이번 범위에 포함하지 않는다.

#### FR-2: 프로그램(루틴) 선택

- [ ] FR-2.1: `AppState`에 현재 수행 중인 프로그램 정보를 추가한다.
      최소한 **프로그램 id**와 **그 구간의 시작일(`startedAt`)** 을 담아야 한다.
      `startedAt`은 사용자가 프로그램을 **고른 날이 아니라, 그 루틴의 첫 운동일**이다 (FR-2.6).
- [ ] FR-2.2: 선택 가능한 프로그램은 `data/progressions.json`의 5종이다.
      `new_blood`, `good_behavior`, `veterano`, `solitary_confinement`, `supermax`
- [ ] FR-2.3: 사용자가 고를 수 있도록 각 프로그램의 **설명 데이터**를 제공하는 조회 API를 만든다.
      최소 포함 항목:
      - 프로그램 id / 이름(en, ko)
      - 빈도 설명 (`frequency`, 예: `"주 3회 (격일)"`)
      - **운동일 수 / 휴식일 수** (주 7일 기준으로 계산)
      - **다루는 종목 목록** (`ProgressionId[]`, 중복 제거)
      - **보조 운동 목록** (빅6에 없는 항목: 악력·종아리·목 운동)
      - 프로그램 `note` (있으면)
      - 이 값들은 `catalog`에서 **파생 계산**한다. JSON에 중복 저장하지 않는다.
- [ ] FR-2.4: 프로그램을 선택하면 **선택한 날짜부터** 그 프로그램의 요일표를 따른다.
- [ ] FR-2.5: **프로그램 미선택 상태**에서 "오늘 계획"을 요청하면 계획을 만들지 않고,
      **프로그램 선택으로 유도하는 신호**를 반환한다(예외를 던지지 않는다).
      호출자가 분기할 수 있는 명시적 값이어야 한다.
- [ ] FR-2.6: **구간 시작일(`startedAt`)은 그 루틴의 첫 운동일이다.** *[확정]*
      선택일이 해당 루틴의 운동일이면 선택일이 곧 첫 운동일이다.
      선택일이 **휴식일**이면 그 다음으로 오는 **첫 운동일**이 `startedAt`이 된다.
- [ ] FR-2.7: **며칠차 = `startedAt`으로부터의 경과일 + 1** (달력 기준).
      `startedAt` 당일이 1일차다. `startedAt` **이전** 날짜를 조회하면 **0**이다 (EC-10과 일관).

#### FR-3: 프로그램 전환 (수동)

- [ ] FR-3.1: 사용자는 언제든 다른 프로그램으로 전환할 수 있다.
- [ ] FR-3.2: 전환하면 **그날부터** 새 루틴을 따른다.
      새 구간의 `startedAt`은 FR-2.6과 동일한 규칙으로 정한다 — 전환일이 새 루틴의 휴식일이면
      **다음 첫 운동일**이 `startedAt`이 된다.
- [ ] FR-3.3: 이전에 수행했던 프로그램으로 되돌아와도 **이어가기는 없다.**
      항상 **새 구간**으로 취급하며, "며칠차"는 1부터 다시 센다.
- [ ] FR-3.4: 지난 구간 이력은 `AppState`에 보존한다(`pastPrograms` 등).
      각 구간은 최소 `{ programId, startDate, endDate }`를 갖는다.
- [ ] FR-3.5: 프로그램 전환은 `AppState.steps`(종목별 현재 단계)와 `history`를 **변경하지 않는다.**
      단계 진행은 프로그램과 독립적이다.
- [ ] FR-3.6: **과거 이력은 무제한 누적한다.** *[확정 사양]*
      `pastPrograms`에 **개수 상한이나 보관 기간 제한을 두지 않으며, 자동 정리(pruning)도 하지 않는다.**
      오래된 구간을 잘라내는 로직을 구현해서는 안 된다.
      `history`(세션 기록) 역시 동일하게 무제한 누적한다.

#### FR-4: 자동 전환 제안

- [ ] FR-4.1: 제안 조건 — 현재 루틴이 다루는 **모든 종목**이 아래를 달성했을 때: *[확정 사양]*
      1. 상급자(intermediate/progression 등 해당 단계의 상위) 기준을 충족해
      2. **다음 단계로 승급**했고
      3. 승급 이후 **그 종목의 세션을 3회 이상** 강등 없이 수행했다.
- [ ] FR-4.2: **"3회"의 기준**은 그 종목의 **세션 3회**다. 날짜 3일도, 주 3회도 아니다.
      `kind`가 `work`이든 `consolidation`이든 그 종목의 세션이면 카운트한다.
- [ ] FR-4.3: **강등의 정의** — 도전 중 사용자가 '불가능'을 눌러 이전 단계 다지기 세션으로 내려간 것.
      데이터상으로는 `outcome: 'abandoned'` 기록 또는 그로 인해 발생한
      `kind: 'consolidation'` 세션의 조합으로 판정한다.
- [ ] FR-4.4: 카운트 도중 **추가 승급**이 일어나도 카운트를 **리셋하지 않는다.**
      추가 승급은 판정에 무관하다.
- [ ] FR-4.5: 아직 **해금되지 않은 종목**(`checkGate`가 `unlocked: false`인 `bridge` / `hspu`)은
      판정 대상에서 **제외**한다. 잠긴 종목 때문에 제안이 영영 뜨지 않는 상황을 막는다.
- [ ] FR-4.6: **제안의 생성(판정)은 월요일에만** 한다. 주간 단위 루틴이므로,
      주중에 조건을 채워도 그 주에는 제안이 새로 생기지 않는다.
- [ ] FR-4.6a: 한 번 생성된 제안은 **승인 또는 거절 기록이 남기 전까지 매일 노출된다.**
      사용자가 월요일에 앱을 열지 않아도 화요일·수요일에 그대로 보인다.
- [ ] FR-4.6b: 따라서 제안은 **미결(pending) / 승인(accepted) / 거절(declined)** 상태를 갖는
      데이터로 상태에 저장되어야 한다. 매 조회마다 새로 계산되는 휘발성 값이 아니다.
      미결 제안은 한 시점에 최대 하나다.
- [ ] FR-4.7: 제안 순서는 고정이다.
      `new_blood → good_behavior → veterano → solitary_confinement → supermax`
      현재 프로그램의 **다음 순번** 하나를 제안한다. `supermax`에서는 제안하지 않는다.
- [ ] FR-4.8: 사용자가 **승인**하면 FR-3의 수동 전환과 **동일하게** 즉시 전환한다.
      **승인 시점이 월요일이 아니어도 승인한 그날부터** 새 루틴이 시작된다
      (구간 시작일은 FR-2.6에 따라 새 루틴의 첫 운동일).
- [ ] FR-4.9: 사용자가 **거절**하면 현 루틴을 유지하고 그 제안은 사라진다.
      **쿨다운도 영구 차단도 없다.** 다음 월요일에 조건이 유지되고 있으면
      같은 제안이 **다시 생성된다.** 즉 조건이 만족되는 한 매주 월요일에 계속 제안한다.
      거절 이력(`declinedSwitches` 등)은 조회·통계 목적으로 남길 수 있으나,
      **재제안을 막는 용도로 쓰지 않는다.**
- [ ] FR-4.10: 제안 판정 함수는 **순수 함수**이며, 제안이 없을 때는 `null`을 반환한다.

#### FR-5: 수행 기록 조회

- [ ] FR-5.1: 특정 날짜에 대해 다음을 조회할 수 있어야 한다.
      - 날짜 (YYYY-MM-DD)
      - 그날 수행 중이던 **프로그램 id**와 **며칠차**
      - 그날 계획되어 있던 종목·목표
      - 그날 실제 수행한 기록(종목, 단계, 세트별 수치, RPE, `kind`, `outcome`)
- [ ] FR-5.2: 기간(시작일~종료일) 단위 조회를 제공한다.
- [ ] FR-5.3: **미수행일도 결과에 남아야 한다.**
      계획이 있었는데 기록이 없는 날은 `'missed'`(미수행) 상태로 표시한다.
      계획 자체가 없던 날은 `'rest'`(휴식일)로 구분한다.
      즉 하루의 상태는 최소 `rest` / `done` / `partial` / `missed` 로 구분 가능해야 한다.
- [ ] FR-5.4: 구간 시작일(`startedAt`, 곧 첫 운동일) **이전** 날짜를 조회하면 **며칠차는 0**이다.
      선택일과 첫 운동일 사이의 휴식일들도 며칠차 0으로 취급한다 (FR-2.6/FR-2.7).
- [ ] FR-5.5: 조회는 상태를 변경하지 않는 순수 함수다.

#### FR-6: 실제 달력 요일 사용

- [ ] FR-6.1: `Date` 또는 `'YYYY-MM-DD'` 문자열에서 요일을 도출해 그날의 계획을 산출하는
      날짜 기반 API를 제공한다.
- [ ] FR-6.2: 요일 매핑은 기존 `Weekday`(`'월'~'일'`) 타입을 그대로 사용한다.
      JS `Date.getDay()`의 0=일요일과의 변환을 정확히 처리한다.
- [ ] FR-6.3: 시간대는 **로컬 타임존**을 기준으로 한다. 날짜 문자열 파싱 시
      UTC 해석으로 하루가 밀리지 않도록 주의한다.
- [ ] FR-6.4: `planDay`의 요일 문자열 인터페이스는 내부용으로 유지할 수 있으나,
      외부 진입점은 날짜 기반이어야 한다(→ Constraints의 `planDay` 시그니처 정리 참조).

#### FR-7: 세션 진행 흐름 (엔진 API 관점)

- [ ] FR-7.1: 사용자가 도전 중 '불가능'을 입력하면 해당 세션을 `outcome: 'abandoned'`로 기록한다.
- [ ] FR-7.2: 그 직후 "이전 단계 다지기를 하겠는가" 확인을 거쳐 승인하면,
      그날 바로 이전 단계 다지기 세션(`kind: 'consolidation'`, `performedStep = step - 1`)을 진행한다.
- [ ] FR-7.3: 다지기 목표 계산 로직 자체는 `planConsolidation` / `canConsolidate` /
      `consolidationCount`에 **이미 구현되어 있다. 재구현하지 않는다.**
      이번 작업은 이 로직을 **상태 갱신 및 기록과 연결**하는 것이다.
- [ ] FR-7.4: **1단계에서 '불가능'** 인 경우 내려갈 단계가 없다.
      다지기를 만들지 않고 **현 단계를 그대로 유지**한다. `canConsolidate`가 `false`를 반환해야 한다.
- [ ] FR-7.5: 하루에 **같은 종목을 두 번** 기록할 수 있다. 두 기록 모두 남기고 승급 판정은 **각각** 수행한다.

### Secondary Features

- [ ] FR-8: `SessionRecord`에 **승급 결과 필드**를 추가한다.
      FR-4의 "승급 후 세션 3회 유지" 판정을 위해 과거 세션을 재평가하지 않아도 되게 한다.
      (→ Constraints의 충돌 3번 참조)
- [ ] FR-9: 기존 RPE 규칙은 그대로 유지한다.
      - 승급 거부권: 최근 3회 평균 RPE ≥ 8이면 승급 보류
      - 목표 하향: 직전 RPE ≥ 9이면 유지세트 −1
      - 심박수는 사용하지 않는다.
- [ ] FR-10: `initialState()`는 프로그램 미선택 상태를 기본값으로 반환한다.

## Non-Functional Requirements

### Dependencies
- [ ] NFR-1: **의존성 0을 유지한다.** 외부 npm 패키지를 추가하지 않는다.
      Node 24 내장 타입 스트리핑 + 내장 테스트 러너(`node --experimental-strip-types --test`)만 사용한다.

### Purity
- [ ] NFR-2: 모든 신규 함수는 **순수 함수**다. 인자로 받은 `AppState`를 변형하지 않고
      **새 값을 반환**한다. 기존 `applySession`의 방식을 따른다.

### Testing
- [ ] NFR-3: **기존 테스트를 그대로 통과시킬 의무는 없다.**
      설계 변경으로 기존 테스트(커밋 `531fb61` 기준 47개)가 깨지는 것은 **허용되며**,
      변경된 구조에 맞게 **다시 작성한다.** 기존 테스트는 작은 테스트용 모듈이었으므로
      재사용 여부는 설계 판단에 맡긴다.
      단, **동작 보존 사양**(Constraints 참조)을 검증하던 케이스는
      형태가 바뀌더라도 **동등한 검증이 새 테스트에 남아 있어야 한다.**
- [ ] NFR-4: 신규 기능(FR-1~FR-10)에 대한 테스트를 추가한다. 목표 커버리지 ≥ 70%.
      Edge Cases 절의 11개 항목은 각각 테스트 케이스로 존재해야 한다.

### Determinism

      날짜는 항상 **인자로 주입**받아 테스트가 결정적이도록 한다.

### UI Principle (다음 작업으로 전달)
- [ ] NFR-6: 백분율 동기부여 · 격려 문구 · 게이미피케이션을 넣지 않는다. **사실만 표시한다.**
      엔진이 반환하는 `reason` 등 문자열도 이 원칙을 따른다.

## Constraints

### Technical Constraints
- 언어/런타임: TypeScript, Node 24 (타입 스트리핑, 내장 테스트 러너)
- 외부 의존성: **없음** (추가 금지)
- 라이선스: MIT / 공개 저장소 `github.com/U-lis/bigsix`
- 기준 커밋: `531fb61`

### 재설계 자유도 — 무엇이 고정이고 무엇이 자유인가

**핵심 구분**: 이번 작업에서 고정된 것은 **계산 규칙(동작)** 이지,
그것을 담는 **코드 구조**가 아니다.

#### (a) 동작 보존 사양 — 반드시 유지 (변경 금지)

아래 규칙들은 원서에서 나온 **사양**이다. 결과가 달라지면 안 된다.

- **해금 게이트**: 브리지·핸드스탠드는 빅4(pushup/squat/pullup/legraise)가
  **전부 6단계를 완수하고 7단계에 진입**해야 해금된다.
- **진급 판정 플로우차트**: 책의 목표 산출 흐름 — 90% 규칙, 유지세트 = 직전 평균,
  상급자 2세트/3세트 분기, 워밍업 최대 2세트.
- **승급 판정**: 수행 **횟수로만** 판정한다.
- **다지기 증량**: 다지기 3회 누적마다 수행량을 기준의 **10%씩 증량** (30 → 33 → 36 → 39).
- **RPE 정책**: 승급 거부권(최근 3회 평균 ≥ 8이면 보류) + 목표 하향(직전 ≥ 9이면 유지세트 −1).
  **심박수는 사용하지 않는다.**

#### (b) 자유롭게 재설계 가능

- **모듈 경계 · 파일 구성 · 함수 시그니처 · 타입 이름**은 전부 재설계 대상이다.
- 기존 파일을 합치거나 쪼개거나 이름을 바꿔도 된다. 새 구조가 더 낫다면 새로 설계한다.
- 기존 함수를 그대로 호출할지, 로직만 옮겨 새 함수로 만들지는 **설계 단계에서 결정**한다.

#### (c) 변경 대상이 아닌 것 (제약 유지)

- **`data/progressions.json`의 데이터 스키마와 그 안의 수치는 변경하지 않는다.**
  60단계 데이터, 프로그램 5종 요일표, `perSide` 플래그 모두 현재 값 그대로 사용한다.

#### 재사용 권장 — 현재 구현 인벤토리

아래는 (a)의 규칙이 이미 구현되어 동작하는 지점이다.
**그대로 호출하는 편이 안전하지만, 재설계 시 대체해도 무방하다.**
다만 대체할 경우 (a)의 동작이 보존되는지 테스트로 증명해야 한다.

| 파일 | 함수 | 역할 |
|------|------|------|
| `src/gate.ts` | `checkGate`, `unlockedProgressions` | 브리지·핸드스탠드 해금 판정 (빅4가 전부 6단계를 완수하고 7단계에 진입해야 해금) |
| `src/plan.ts` | `planExercise`, `planWarmup` | 책 플로우차트대로 다음 세션 목표 계산 (90% 규칙, 유지세트=직전평균, 상급자 2/3세트 분기, 워밍업 최대 2세트) |
| `src/plan.ts` | `planConsolidation`, `canConsolidate`, `consolidationCount` | 다지기. 3회 누적마다 수행량 10% 증량 (30 → 33 → 36 → 39) |
| `src/evaluate.ts` | `evaluateSession`, `applySession` | 승급 판정. 수행 횟수로만 판정 |
| `src/schedule.ts` | `planDay`, `planWeek`, `getProgram`, `listPrograms` | 요일별 계획 |
| `src/history.ts` | `sessionsAt`, `lastSession`, `mean`, `meetsStandard` | 기록 조회 헬퍼 |

### 기존 구현과의 충돌 — 반드시 해결할 것

#### 충돌 1: `AppState` 스키마 변경 (Breaking)
- 현재: `AppState = { steps: Record<ProgressionId, number>; history: SessionRecord[] }`
- 필요: `program`(현재 구간), `pastPrograms`(지난 구간들), `declinedSwitches`(거절 이력) 추가
- 추가로 FR-4.6b에 따라 **미결 제안(pending/accepted/declined 상태)** 을 담을 자리도 필요하다.
- **영향**: `initialState()` 반환값이 바뀐다. 기존 테스트 47개가 영향받는다.
- **결정**: 0.1.0 첫 기능 릴리스이므로 **하위 호환을 유지하지 않는다.**
  새 필드는 선택적(optional)으로 두지 말고 명시적으로 정의한다.
  기존 테스트는 NFR-3에 따라 새 구조에 맞게 다시 작성한다.
  필드 이름과 중첩 구조(`program` / `pastPrograms` / `declinedSwitches` / 제안 상태)는
  **예시일 뿐이며 설계 단계에서 확정한다.**

#### 충돌 2: `planDay` 시그니처 중복 — **설계 단계에서 결정**
- 현재: `planDay(state, catalog, programId, weekday)`
- 상태에 프로그램이 생기면 `programId` 인자가 **상태와 중복**된다.
- **이 SPEC은 해결 방식을 고정하지 않는다.** 모듈 경계와 시그니처는 재설계 자유 영역이므로
  (위 "재설계 자유도" 참조) 설계 단계에서 정한다.
- 참고용 대안:
  - (안 A) `planDay`/`planWeek`를 명시적 인자를 받는 저수준 함수로 유지하고,
    상태의 현재 프로그램 + 실제 날짜를 쓰는 **날짜 기반 상위 진입점을 추가**한다.
  - (안 B) `planDay`에서 `programId` 인자를 제거하고 **상태에서 읽도록 통합**한다 (breaking).
  - (안 C) 스케줄 모듈 자체를 날짜 중심으로 **재작성**한다.
- 어느 안을 택하든 **FR-2.5**(프로그램 미선택 시 유도 신호 반환)와
  **FR-6**(날짜 기반 진입점)은 만족해야 한다.

#### 충돌 3: 승급 사실이 기록에 남지 않는다
- 현재 `SessionRecord`에는 "이 세션에서 승급했다"는 정보가 **없다.**
- FR-4의 "승급 후 세션 3회 유지"를 판정하려면 과거 세션을 **재평가**해야 하는데,
  **RPE 거부권으로 보류된 건은 재현이 어렵다**(당시의 최근 3회 RPE 맥락에 의존).
- **결정**: `SessionRecord`에 승급 결과 필드를 추가한다(FR-8).
  최소한 "이 세션 결과로 단계가 올라갔는가"와 "올라간 결과 단계"를 담는다.
  `applySession`이 이 값을 채워 기록한다.

#### 충돌 4: 강등 판정은 기존 데이터로 가능
- `outcome: 'abandoned'` + `kind: 'consolidation'` 조합으로 판정 가능하다.
- 이 부분은 **스키마 변경이 필요 없다.**

## Out of Scope

이번 작업에 **포함되지 않는다.**

- **UI / 화면 전부** — 다음 작업으로 분리한다. 이번 범위는 **엔진만**이다.
- **주간 · 월간 캘린더 뷰** — 별도 GitHub 이슈로 분리 예정
- **심박수 입력** — 사용하지 않기로 결정됨. RPE만 사용한다.
- **저장(persistence) 계층** — 파일/DB 영속화는 다루지 않는다. 엔진은 `AppState`를 인자로 받고 반환만 한다.
- 좌/우를 각각 분리 저장하는 기록 모델 (FR-1은 약한 쪽 하나만 저장한다)
- 프로그램 5종 외의 커스텀 루틴 정의

## Assumptions

- A-1: 사용자는 하루에 여러 종목을 기록할 수 있고, 각 기록은 독립적으로 판정된다.
- A-2: 프로그램의 요일표(`Program.schedule`)는 **주 단위로 반복**된다. 격주·4주 주기 같은 변형은 없다.
- A-3: '며칠차'는 구간 시작일(`startedAt` = 첫 운동일)로부터의 **달력 일수 + 1** 기준이며,
  운동 수행 여부와 무관하다(EC-8).
- A-4: 프로그램 구간은 서로 겹치지 않으며 한 시점에 활성 구간은 최대 하나다.
- A-5: 날짜는 `'YYYY-MM-DD'` 문자열로 표현하고 로컬 타임존으로 해석한다.
- A-6: 승급 판정 기준(상급자 기준)은 Constraints (a)의 **동작 보존 사양**을 따른다.
  FR-4는 그 결과를 소비할 뿐 판정 기준을 재정의하지 않는다.
  판정 로직이 어느 모듈에 있는지는 설계 자유 영역이다.
- A-7 (출처 표기): FR-4의 자동 전환 조건 — "상급자 기준 충족 → 승급 → 그 종목 세션 3회 유지" — 은
  **원서 인용이 아니라 사용자가 정한 규칙**이다. 원서 12장 본문은 미확보 상태다.
  이는 출처를 사실대로 밝히는 기록일 뿐이며, **규칙 자체는 확정되어 재검토 대상이 아니다.**

> - ~~기존 테스트 47개 통과 유지~~ → **의무 아님.** 구조 재설계 허용 (NFR-3, Constraints)
> - ~~자동 전환 조건의 근거 (원서 12장 미확보)~~ → **사용자가 정한 규칙으로 확정.**
>   "승급 → 유지" 조건 그대로 간다. 재검토 예정 없음 (FR-4.1, A-7)
> - ~~`pastPrograms` 누적 상한~~ → **무제한 누적으로 확정.** 상한·정리 정책 없음 (FR-3.6)
