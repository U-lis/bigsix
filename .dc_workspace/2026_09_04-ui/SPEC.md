# bigsix UI (SvelteKit PWA) - Specification

**Target Version**: 0.2.0
**Work Type**: feature
**Base Branch**: `main` (`832424a`)
**Working Branch**: `feature/ui`
**Source Conversation**: prefill

---

## Overview

**Purpose**
0.1.0 에서 완성된 도메인 로직(순수 함수, 테스트 474개, line 커버리지 100%) 위에
**사람이 실제로 쓰는 화면**을 얹어, 폰 홈화면에 설치해 쓰는 하나의 PWA 앱으로 만든다.

**Problem**
문제는 두 층이다.

*(1) 기능이 없다.* 저장소에 UI 가 전혀 없고, 도메인 로직은 `AppState` 를 받아 새 `AppState` 를
돌려줄 뿐이라 다음 세 가지가 비어 있다.

- **저장(persistence) 계층이 없다.** 엔진 SPEC 의 Out of Scope 가 명시적으로 제외했다.
  앱을 껐다 켜면 상태가 사라진다.
- **"오늘이 며칠인가" 를 아는 주체가 없다.** 도메인은 NFR-5 로 시스템 시각을 읽지 않는다.
  날짜는 항상 `IsoDate`('YYYY-MM-DD') 로 **주입**받는다.
- **진행 중 세션을 표현할 타입이 없다.** `SessionRecord` 는 **완결된** 세션만 표현한다.
  세트 3개 중 2개까지 한 상태를 담을 자리가 도메인 타입에는 없다.

*(2) 구조의 전제가 틀렸다.* 0.1.0 은 "의존성 0 의 독립 엔진 패키지" 로 설계됐다.
그러나 **그것은 사용자 요구가 아니었고, 스택이 정해지기 전 임시로 잡은 전제였다.**
스택이 CubeStudy 와 같은 SvelteKit PWA 로 확정된 지금 그 전제는 사라졌다 (D-6).

그 결정은 실제로 비용을 냈다 — 의존성 0 때문에 `tsc` 를 쓸 수 없었고,
`applySession` 이 세션마다 새 필드를 소리 없이 버리던 Critical 결함을
**컴파일러가 아니라 사람이 코드를 읽어서** 잡아야 했다.

**Solution**
저장소를 **SvelteKit 앱 하나**로 재구성한다 (`package.json` 하나, 테스트 러너 하나, 타입 검사 있음).
기존 `src/*.ts` 는 `src/lib/domain/` 으로 **이동만** 하고 로직은 건드리지 않는다.
그 위에 localStorage 저장 계층과 화면 3개(오늘 세션 / 프로그램 선택 / 단계 현황)를 얹는다.
**계산 로직은 하나도 새로 만들지 않는다.** 도메인 함수를 호출할 뿐이다.

**도메인은 고정 자산이 아니다** (D-19). 0.1.0 의 도메인은 UI 요구가 정해지기 전에 만들어졌고,
사용성을 반영하지 못한 부분이 있는 것이 당연하다. 사용자가 요구하면 도메인도 바꾼다 —
이번 작업에서 이미 보조 운동 제거(FR-12)와 단계 수동 세팅(FR-13)이 그 경우다.
바꾸지 말자는 것이 아니라, **구조 이관 커밋과 동작 변경 커밋을 섞지 말자**는 것이 FR-0.8 이다.

## 확정 사항 (사용자 결정, 재검토 대상 아님)

| # | 항목 | 결정 |
|---|---|---|
| D-1 | 스택 | **SvelteKit + TypeScript + vitest + PWA(`adapter-static`)**. CubeStudy 와 동일. 서버 없음, 정적 배포 |
| D-2 | 저장 | **localStorage** 에 `AppState` 전체를 JSON 직렬화. 스키마 버전 필드를 둔다 |
| D-3 | 진행 중 세션 | **세트마다 저장하고, 재실행 시 그 자리부터 복원**한다 |
| D-4 | 첫 버전 화면 | **오늘 세션 / 프로그램 선택 / 단계 현황** 3개 |
| D-5 | 수행 기록 목록 | **범위 밖.** 캘린더 뷰(이슈 #1)와 함께 다음 작업으로 미룬다 |
| D-6 | 저장소 구조 | **단일 SvelteKit 앱.** 별도 엔진 패키지를 두지 않는다. `package.json` 하나. 도메인 로직은 `src/lib/domain/` 으로 이동 |
| D-7 | 자정을 넘긴 세션 | **세션을 시작한 날짜로 기록한다.** 자정이 지났다고 중단하고 다음날 것을 하지 않는다 |
| D-8 | 데이터 내보내기·가져오기 | **제공하지 않는다.** 범위 밖 |
| D-9 | 여러 탭 동시 사용 | **마지막 쓰기 우선.** 감지도 잠금도 하지 않는다. PWA 를 여러 탭으로 여는 것은 상정하지 않는다 |
| D-10 | 세트 수치 입력 | **숫자 키패드 직접 입력**(`type="number"`). 기본값은 그 세트의 목표 수치. 스크롤 휠은 세 자리에서 느려 폐기 |
| D-11 | RPE 입력 | **세트마다** 받는다. 도메인은 세션당 하나만 받으므로 **최댓값**을 세션 RPE 로 넘긴다 |
| D-12 | 타이머 | `unit: 'seconds'` 단계에 **내장 타이머**. 준비 5초 → 카운트업. 목표 도달 시 5초만 알리고 조용해지며, **정지 버튼을 누를 때까지 계속 흐른다.** 정지 시각이 곧 기록이다 |
| D-13 | 수동 단계 조정 | **허용한다.** 도메인에 단계를 직접 세팅하는 API 를 추가한다 |
| D-14 | 첫 실행 시작 단계 | **사용자가 고른다.** 기본값은 책 권고대로 전 종목 2단계 |
| D-15 | 표시 언어 | **한국어 고정.** 다국어는 하지 않는다 |
| D-16 | 배포 | **홈서버 정적 배포**(duckdns). CubeStudy 의 `deploy/` 방식을 따른다. GitHub Pages 아님 |
| D-17 | 보조 운동 | **전면 제거.** 빅6 만 남긴다. 화면·도메인 출력에서 모두 뺀다 |
| D-18 | PWA 에셋 | **직접 만든다.** CubeStudy 와 같이 아이콘·스플래시를 이 작업 안에서 생성한다 |
| D-19 | 도메인 변경 권한 | **사용자 요구가 있으면 도메인도 바꾼다.** "엔진 변경 금지" 는 사용자 결정이 아니었다. 하나의 서비스로 다루며, 구조 이관 커밋과 동작 변경 커밋만 분리한다 |

D-2 의 근거: 주 3회 × 2종목이면 연 300건 남짓이다. localStorage 5MB 한도는 수십 년치를 담는다.
용량이 문제가 되는 시점은 예측 가능한 범위 밖이며, 스키마 버전 필드로 이후 마이그레이션 여지만 남긴다.

D-6 의 근거: 참조 구현인 CubeStudy(`~/Documents/cube-study`)는 `package.json` 하나,
`src/lib/domain/`(순수 로직) + `src/lib/data/`(JSON + loader) + `src/lib/ui/`,
`tests/unit/`(vitest), `check: svelte-kit sync && svelte-check` 구성이며
**엔진을 별도 패키지로 두는 개념 자체가 없다.**
같은 스택을 쓰기로 확정한 이상 bigsix 만 별도 패키지를 유지할 이유가 없다.
구조 이관은 **별도 리팩터링 작업이 아니라 이번 작업에 포함**한다 (사용자 결정).

D-11 의 근거: 도메인의 RPE 용도는 두 가지뿐이다 — 승급 거부권(최근 3회 평균 ≥ 8)과
목표 하향(직전 ≥ 9). 둘 다 **부하가 높을수록 보수적으로 작동**한다.
세트별 값 중 최댓값을 쓰면 부하를 낮게 잡는 실수가 생기지 않는다.
본세트 후반이 가장 힘든 것이 정상이므로 최댓값은 대개 마지막 세트 값과 같다.

D-10 의 근거: "한 세트에 100회 이상이 있나" 의 답은 **있다** —
푸시업 10단계(한손 푸시업) 상급 기준이 `1×100` 이고, `unit: 'seconds'` 의 최댓값은
핸드스탠드 진행 기준의 `120`(초)다. 세 자리가 필요하고, 세 자리를 스크롤로 맞추는 것은
느리다. 그래서 스크롤 휠을 버리고 **숫자 키패드 직접 입력**으로 간다.
`unit: 'seconds'` 는 애초에 타이머가 기록하므로 입력 대상이 아니다 (D-12).

D-12 의 근거: 정지 버튼까지 계속 흐르게 하는 이유는 **목표를 넘겨 버티는 것이 정상**이기 때문이다.
`mode: 'max'` 세트는 "이 수치를 상한으로" 가 아니라 "최대한" 이며, 초과분이 승급 근거다.
목표에서 자동으로 멈추면 그 초과분을 버린다.

D-19 의 근거: 이전 개정은 "도메인 로직 변경" 을 Out of Scope 에 넣었다.
**그것은 사용자 결정이 아니라 이 SPEC 이 혼자 세운 제약이었다.**
0.1.0 도메인은 UI 요구가 확정되기 전에 만들어졌으므로 사용성을 반영하지 못한 곳이 있는 것이
정상이고, 그 책임은 도메인을 그렇게 설계한 쪽에 있다. 앱은 하나의 서비스이며 도메인은 그 일부다.
D-13 · D-14 · D-17 이 도메인 변경을 요구하는 것은 "예외" 가 아니라 **정상적인 범위**다.
다만 **커밋은 나눈다** (FR-0.8, Notes 커밋 분리 지침).

## Functional Requirements

### FR-0: 저장소 구조 이관 (단일 SvelteKit 앱)

- [ ] FR-0.1: 저장소를 **SvelteKit 앱 하나**로 재구성한다. `package.json` 은 **하나**다.
- [ ] FR-0.2: `src/*.ts` 를 **`src/lib/domain/` 으로 이동**한다.
      **파일 이름과 내용을 유지**한다. 로직·타입·시그니처를 바꾸지 않는다.
      (`types.ts` `rules.ts` `catalog.ts` `gate.ts` `history.ts` `plan.ts` `evaluate.ts`
      `schedule.ts` `date.ts` `program.ts` `proposal.ts` `session.ts` `calendar.ts` `index.ts`)
- [ ] FR-0.3: `data/progressions.json` 을 **`src/lib/data/` 로 이동**한다.
      **내용은 무변경**이며, 스키마·수치 변경 금지 제약은 그대로 유지된다.
- [ ] FR-0.4: 테스트 러너를 `node --experimental-strip-types --test` 에서 **vitest** 로 바꾸고,
      `test/` 를 **`tests/unit/`** 으로 옮긴다. 단언 API 가 거의 같으므로 **기계적 이관**이다.
- [ ] FR-0.5: **기존 테스트 474개가 전부 살아남아야 한다.** 이관 과정에서 삭제·스킵되는 케이스가 없어야 하며,
      이관 후에도 전부 통과해야 한다. 커버리지도 이관 전 수준(line 100%)을 유지한다.
- [ ] FR-0.6: **`svelte-check` 로 타입 검사를 도입한다.** `check` 스크립트를 제공하며,
      도메인 코드와 UI 코드 모두 타입 검사 대상이다. **이것이 이번 구조 변경의 실질적 이득이다.**
- [ ] FR-0.7: `catalog.ts` 의 `loadCatalog` 는 `node:fs` 에 의존해 브라우저에서 동작하지 않는다.
      **제거하거나 Node 전용으로 격리**한다. 앱 코드 경로에서 `node:fs` 가 import 되지 않아야 한다.
      (현재 사용처: `src/index.ts` 의 재export, `test/helpers.ts`, `test/tz-probe.ts`)
- [ ] FR-0.8: **구조 이관 자체는 동작을 바꾸지 않는다.** 이관 커밋에서는 파일이 옮겨질 뿐이며,
      계산 규칙을 함께 손대지 않는다. 이것은 "도메인을 영원히 바꾸지 말라" 는 뜻이 **아니다** (D-19).
      동작 변경은 **이관이 끝난 뒤 별도 커밋**으로 한다. 이유는 리뷰 가능성이다 —
      이동 diff 와 로직 diff 가 한 커밋에 섞이면 무엇이 바뀌었는지 읽을 수 없다.
- [ ] FR-0.9: 이관 후 도메인 로직의 공개 진입점은 `src/lib/domain/index.ts` 이며,
      UI 는 이 진입점을 통해서만 도메인을 참조한다. 개별 모듈을 직접 import 하지 않는다.

### FR-1: 저장 계층 (localStorage)

- [ ] FR-1.1: `AppState` 전체를 **JSON 문자열 하나**로 localStorage 에 저장한다.
- [ ] FR-1.2: 저장 데이터는 **스키마 버전 필드**를 포함한다.
      저장 형태는 최소 `{ schemaVersion, appState }` 를 담는 봉투(envelope)여야 하며,
      `AppState` 자체에 버전 필드를 섞지 않는다 (도메인 타입을 오염시키지 않는다).
- [ ] FR-1.3: 앱 부팅 시 저장된 값을 읽어 복원한다. 저장된 값이 없으면 `initialState()` 로 시작한다.
- [ ] FR-1.4: 읽은 값의 `schemaVersion` 이 앱이 아는 버전보다 **낮으면** 마이그레이션을 시도한다.
      0.2.0 시점에는 마이그레이션 대상이 없으므로 **경로만 만들고 변환은 없다.**
- [ ] FR-1.5: `schemaVersion` 이 앱이 아는 버전보다 **높으면**(구버전 앱이 신버전 데이터를 만난 경우)
      데이터를 건드리지 않고 **읽기 실패로 처리**하며, 덮어쓰지 않는다.
- [ ] FR-1.6: 상태를 바꾸는 모든 조작(프로그램 선택·전환, 제안 승인·거절, 세션 기록, 도전 포기) 직후
      저장한다. 저장 실패는 조용히 넘기지 않는다 (→ FR-1.8).
- [ ] FR-1.7: **손상된 저장 데이터**(JSON 파싱 실패, 필수 필드 누락, 타입 불일치)를 만나면
      자동으로 지우지 않는다. 원본을 보존한 채 사용자에게 사실을 알리고
      **"초기 상태로 시작" 을 사용자가 명시적으로 선택**하게 한다.
- [ ] FR-1.8: 저장 실패(용량 초과, 사생활 보호 모드로 인한 접근 차단 등)를 감지하면
      **화면에 사실을 표시**한다. 실패한 채로 계속 쓰게 두지 않는다.
- [ ] FR-1.9: 저장 계층은 도메인 타입을 **가공하지 않고 그대로** 직렬화한다.
      UI 전용 파생값(표시용 라벨 등)을 저장 데이터에 섞지 않는다.

### FR-2: 진행 중 세션 (UI 전용 스키마)

- [ ] FR-2.1: **`SessionRecord` 로는 진행 중 세션을 담을 수 없다.**
      `SessionRecord` 는 완결된 세션만 표현하므로, **UI 쪽 별도 스키마**를 정의한다.
- [ ] FR-2.2: 진행 중 세션은 최소한 다음을 담는다.
      - **세션을 시작한 날짜**(`IsoDate`) — 완료 시 `SessionInput.date` 가 되는 값 (FR-2.8)
      - 대상 종목(`ProgressionId`)과 훈련 단계(`step`) / 수행 단계(`performedStep`)
      - 세션 종류(`kind: 'work' | 'consolidation'`)
      - **지금까지 입력한 세트 값 배열** (워밍업 / 본 세트 구분 포함)
      - 아직 완결되지 않았다는 표시
- [ ] FR-2.3: **세트 값을 하나 입력할 때마다** 진행 중 세션을 저장한다.
      운동 중 전화를 받거나 앱이 죽어도 입력한 세트를 잃지 않는다 (D-3).
- [ ] FR-2.4: 앱 부팅 시 저장된 진행 중 세션이 있으면 **그 자리부터 복원**한다.
      복원 대상 화면은 오늘 세션 화면이며, 이미 입력한 세트는 입력된 상태로 보인다.
- [ ] FR-2.5: 세션을 마치면 도메인의 `recordSession`(또는 다지기의 `recordConsolidation`)을 호출해

### FR-6: 세트 입력

- [ ] FR-6.1: 세트별 수치를 하나씩 입력하며, **입력할 때마다 저장**한다 (FR-2.3).
- [ ] FR-6.2: `unit === 'reps'` 인 단계는 **횟수**를 직접 입력받는다 (D-10).

      최대 목표가 100(푸시업 10단계 상급)이라 세 자리가 필요하고,

- [ ] FR-6.2a: 입력란의 **초기값은 그 세트의 목표 수치**(`TargetSet.value`)다.

- [ ] FR-6.2b: 음수와 비정수를 거부한다. 상한은 두지 않는다 —
      `mode: 'max'` 세트는 목표를 넘겨 수행할 수 있고, 그것이 승급 근거가 된다.
- [ ] FR-6.3: `unit === 'seconds'` 인 단계는 **유지 시간(초)** 을 기록한다.
      핸드스탠드 1~3단계가 여기 해당한다. **입력 UI 가 횟수 입력과 갈려야 한다.**
      시간은 원칙적으로 **타이머가 기록**하며 사람이 숫자를 치지 않는다 (FR-6.12~6.16).

- [ ] FR-6.5: `perSide === true` 인 단계에서는 `sideNote` 고지를 **반드시 표시**한다.

      해당 단계는 총 16개다 — 푸시업·스쿼트·풀업·핸드스탠드의 7~10단계.

- [ ] FR-6.6: `mode === 'max'` 인 세트는 "**이 수치 이상으로 최대한**",
      `mode === 'fixed'` 인 세트는 "이 수치만큼" 임이 구분되어 보여야 한다.
      `max` 의 목표 수치는 **상한이 아니라 하한**이다 (FR-15).
- [ ] FR-6.7: RPE 를 **세트마다** 입력할 수 있다 (D-11). **선택 입력**이며

- [ ] FR-6.7a: 도메인의 `SessionInput` 은 세션당 RPE 를 하나만 받는다.
      UI 는 입력된 세트 RPE 중 **최댓값**을 세션 RPE 로 넘긴다.
      하나도 입력되지 않았으면 필드를 **비운 채** 넘긴다(0 으로 채우지 않는다).
- [ ] FR-6.7b: 세트별 RPE 원본은 진행 중 세션 스키마(FR-2)에 보존해 복원 대상에 포함한다.

- [ ] FR-6.12: `unit === 'seconds'` 인 세트에는 **내장 타이머**를 제공한다 (D-12).

- [ ] FR-6.13: 타이머는 **항상 올라가는 카운트업**이며, 목표 시간에서 멈추지 않는다 (D-12).

- [ ] FR-6.14: **목표 시간에 도달한 시점에 알린다.** 소리 · 진동 · 화면 점멸을 쓰되

- [ ] FR-6.17: 오작동·오터치에 대비해 기록된 시간을 **수정할 수단은 남긴다.**

## Constraints

### Technical Constraints

- 언어/프레임워크: **TypeScript + SvelteKit** (`adapter-static`)
- 패키지: **단일 `package.json`.** 별도 엔진 패키지·워크스페이스를 두지 않는다 (D-6)
- 테스트: **vitest 하나** (`tests/unit/`)
- 타입 검사: **`svelte-check`** (`check` 스크립트)
- 저장: **localStorage** 만. IndexedDB·서버·클라우드 동기화 없음
- 런타임 서버: **없음.** 정적 파일만으로 동작
- 도메인: `src/lib/domain/` — 로직 변경 없음, 프레임워크·브라우저·Node API 비의존 (NFR-3)
- 데이터: `src/lib/data/progressions.json` — 이번 작업에서는 **이동만** 한다.
  수치는 실물 책과 대조한 기록이라 함부로 바꾸지 않는다. 스키마 확장은 별개 문제이며
  요구가 생기면 바꿀 수 있다 (D-19, 예: 이슈 #3 의 동작 이미지 경로)
- 라이선스: MIT / 공개 저장소 `github.com/U-lis/bigsix`

### 목표 디렉터리 구조 (CubeStudy 준용)

```

src/lib/domain/       # 기존 src/*.ts 를 이름·내용 그대로 이동
src/lib/data/         # progressions.json + 로더
src/lib/ui/           # UI 상태
src/routes/           # 화면 3개
tests/unit/           # 기존 test/*.test.ts 를 vitest 로 이관 (474개 전부)
```

## 알려진 한계 (도메인에서 승계 — UI 가 반드시 인지할 것)

- ~~**L-1: 보조 운동은 수행 판정에서 빠진다.**~~ → **해소.**
  0.1.0 에서는 `accessories` 가 기록되지 않는 참고 필드였고, 그래서 "보이는데 안 세는"
  모순이 있었다. 0.2.0 은 보조 운동을 **전면 제거**해 이 모순 자체를 없앤다 (D-17 / FR-12).
  책의 원래 스케줄은 `progressions.json` 에 그대로 남는다 (FR-12.2).

- **L-2: `DayReview.plannedExercises` 는 그날의 목표가 아니다.**
  조회 시점의 현재 단계로 재계산한 값이라, 그날 이후 단계가 오르내렸으면 수치가 다르다.
  수행 여부 판정의 근거는 종목 목록(`planned`)이지 이 수치가 아니다.

- **L-3: `planOn().rest` 와 `reviewDay().status === 'rest'` 는 다르다.**
  전자는 **그날 요일표가 비었는가**를, 후자는 **판정 대상 종목이 있는가**를 답한다.
  잠긴 종목만 배치된 날은 요일표가 비지 않았어도 `status` 가 `rest` 다. 두 값을 같은 것으로 다루지 않는다.

- **L-4: `'missed'` 는 저장되지 않는 파생 상태다.**
  `stints` + `history` 로부터 매번 다시 계산된다. **UI 가 이 값을 캐싱하면 부정합이 생긴다.**

- **L-5: 0.1.0 에는 타입 검사기가 없었다 — 이번 작업이 이 한계를 해소한다.**
  의존성 0 원칙 때문에 `tsc` 를 쓸 수 없었고, 그 결과 `applySession` 이 세션마다
  새 필드를 소리 없이 버리던 Critical 결함을 **컴파일러가 아니라 사람이 코드를 읽어서** 잡았다.
  이것이 D-6(단일 패키지)과 FR-0.6(`svelte-check` 도입)의 직접적 근거다.
  이관 직후에는 **그동안 검사되지 않던 타입 오류가 새로 드러날 수 있다** (EC-21).

- **L-6: `perSide` 는 16단계다.**
  푸시업·스쿼트·풀업·핸드스탠드의 7~10단계. 레그 레이즈·브리지에는 없으며 이는 데이터 누락이 아니다.
  부위 명칭은 스쿼트가 '다리', 나머지가 '팔' 이지만 **문구 생성은 도메인 책임**이다.

- **L-7: 데이터를 잃으면 복구 경로가 없다.**
  서버가 없고(NFR-7) 내보내기·가져오기도 제공하지 않으므로(D-8),
  브라우저 데이터를 지우거나 기기를 바꾸면 `AppState` 전체 — 단계·기록·프로그램 구간 — 가 사라진다.
  되살릴 수단은 없다.

- **L-8: 세트별 RPE 는 완료 시 사라진다.**
  UI 는 세트마다 RPE 를 받지만(D-11 / FR-6.7), 도메인 `SessionRecord` 는 세션당 하나만
  담는다. 완료하면 **최댓값 하나만** 남고 세트별 값은 복원할 수 없다.
  세트별 보존은 `SessionRecord` 변경이 필요하다. 지금은 요구가 없어 하지 않을 뿐이며,
  필요해지면 바꿀 수 있다 (D-19).

- **L-9: 수동 단계 조정은 되돌릴 수 없다.**
  조정은 `history` 를 남기지 않으므로(FR-13.4) "이전 단계로 돌아가기" 를 자동으로
  제공할 수 없다. 다시 조정해서 되돌리는 것뿐이며, 그때도 유지 횟수는 또 초기화된다(FR-13.3).

  수행 기록 목록이 범위 밖이기 때문이다(D-5). 다만 API 는 이미 존재하므로 재구현하지 않는다.
